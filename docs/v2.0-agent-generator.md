# 模板 Agent Generator 与开发者接管

- 状态：阶段 3 已完成
- 日期：2026-07-30
- 适用分支：Scaffold `v2.0.x-dev`

## 目的

`scripts/muye.sh` 是 v2.0 的本地开发入口。它从任意当前目录定位 Scaffold 根目录，并使用根 `.venv` 执行
受限 Python CLI。Shell 层不保存业务状态、不读取或打印密钥，也不执行 Git、Docker、Milvus 或模型调用。

生成器以已确认、可提交的逻辑输入渲染 `react-knowledge` 模板。它不会接受物理 Collection、数据库地址、
URL、明文密钥、Python 表达式、Dockerfile 片段或任意模板代码。实际知识解析、构建 Job、Milvus 写入和检索
评测属于阶段 4；`knowledge build` 与 `knowledge evaluate` 在此之前会以非零退出码拒绝执行。

## 输入配置

生成一个 Agent 需要两个无密钥 YAML 文件：

```text
config/
  knowledge/<knowledge-slug>.yaml
  agents/<agent-slug>.yaml
```

`config/knowledge/<knowledge-slug>.yaml` 使用 `muye.ai/knowledge-generation-input/v1`，并声明：逻辑
`resource_id`、已确认的 `resource_revision/resource_checksum`、固定版本 `skill_revision/skill_checksum`、
模型 alias、pipeline、固定 scope、字段白名单、预算和评测引用。固定 scope 的字段必须属于
`allowed_filter_fields`，而返回字段必须是受限的逻辑字段名。

`config/agents/<agent-slug>.yaml` 使用 `muye.ai/agent-profile-input/v1`，并声明稳定且不可从 slug 派生的
`agent_id`、Agent 版本、Profile revision 和 `AgentProfileProposalV1`。Profile 只包含展示名、描述、意图、
指令、拒用条件和示例；代码围栏、模板语法、控制字符、可执行 Python、URL、路径、Shell/Docker/依赖命令和
凭据形态都会被拒绝。

两个文件的 `slug` 必须等于命令参数。确认的 checksum 必须使用完整 64 位 SHA-256，小改动必须生成新的
revision/checksum 并重新审阅。审批记录位于 `config/approvals/{resource,skill,profile}/<slug>.json`，包含
subject、revision、checksum、确认人和确认时间，应与输入 YAML 一同纳入 Git。

## 命令

```bash
./scripts/muye.sh knowledge analyze <knowledge-slug>
./scripts/muye.sh knowledge approve-schema <knowledge-slug> --checksum <sha256> --approved-by <principal>
./scripts/muye.sh knowledge approve-skill <knowledge-slug> --checksum <sha256> --approved-by <principal>
./scripts/muye.sh agent approve-profile <agent-slug> --checksum <sha256> --approved-by <principal>

./scripts/muye.sh agent generate <agent-slug> --knowledge <knowledge-slug>
./scripts/muye.sh agent validate <agent-slug>
./scripts/muye.sh agent diff <agent-slug> --template latest
```

`knowledge analyze` 校验当前阶段的逻辑输入并显示 Resource 与 Skill checksum。两个知识确认命令和
`agent approve-profile` 只在传入值精确等于当前配置 checksum 时成功，并将审批写入受控目录，防止看到旧审阅
结果后确认新输入。`agent generate` 在创建 staging 目录前要求 Resource、Skill 和 Profile 三项审批同时精确
匹配，任一缺失或漂移都会失败。阶段 4 将把这些确认接入 Knowledge Worker Job 与不可变发布产物。

`agent generate` 在写入前校验完整 Profile、Knowledge、模板 manifest 和输入 checksum。目标始终是
`agents/agent-<slug>/`；`main`、路径遍历、大小写碰撞、symlink、未知模板变量和既有目录都会失败。所有文件
先在 `agents/` 下的 staging 目录完成 descriptor、compile 和 import smoke，再通过 no-replace 原子 rename
发布。生成器没有 `--force` 或覆盖模式。

`agent validate` 检查 `agent.yaml`、`.muye-generation.json`、`.muye-generation-input.json`、生成文件清单、
symlink 和源码树 checksum。开发者接管后的源码变更会报告 `source_drift: true`，但不会因此否定一个仍完整的
descriptor/provenance 基线。Python bytecode 和 pytest cache 不计入源码树。

`agent diff` 从非敏感的 `.muye-generation-input.json` 在内存中重渲染模板，默认选择本地最新模板；传入
`--template source` 可与产生当前来源记录的精确版本比较。它输出 unified diff，返回 `1` 表示存在差异，且绝不
写入源码、provenance、Git index 或模板。

## 生成产物与接管

首次生成后的目录包含：

```text
agent.py                         # 只读 scoped retrieval ReAct Agent
main.py                          # SDK HTTP 入口
agent.yaml                       # 身份、能力、资源和运行描述的唯一事实源
prompts/system.md                # 已确认 Profile 的简体中文指令
tests/test_contract.py           # 离线 SDK capabilities 契约
Dockerfile
.dockerignore                    # Docker build context 的敏感/本地文件排除规则
requirements.txt                 # 固定 SDK v2.0.0 tag
README.md
.muye-generation.json            # provenance；generated_at 不计入源码 checksum
.muye-generation-input.json      # 无密钥 replay recipe，仅用于 validate/diff
```

`agent.yaml` 是身份、部署和逻辑资源的唯一配置事实源。生成的运行时代码会在启动时严格加载它；不要将同类配置
重新硬编码到 Python 或环境变量。descriptor 的模型 alias、`token_budget` 和 `timeout_seconds` 会覆盖部署环境
中的同类默认值；`tool_budget` 由 ReAct middleware 限制为单次请求中实际执行的工具调用次数。连接地址和密钥
仍只从部署配置读取。`MUYE_AGENT_SERVICE_ID`、`MUYE_AGENT_DEPLOYMENT_ID`、descriptor checksum 和 source
checksum 只由部署层注入，不能来自用户或模型请求。

生成成功后，开发者与 Git 接管源码、Prompt、测试和显式依赖。运行：

```bash
./scripts/muye.sh agent validate <agent-slug>
cd agents/agent-<slug>
../../.venv/bin/python -m pytest -q tests
```

随后提交人工修改并由 CI 构建镜像。阶段 5 的 `agent sync/build/deploy/stop/rollback` 才会处理 Catalog、
Compose、健康检查和发布；本阶段不会将新 Agent 自动注册、启动或暴露给 MainAgent。

## 模板升级

不允许重生成覆盖开发者目录。模板升级采用以下人工迁移过程：

1. 执行 `./scripts/muye.sh agent diff <agent-slug> --template latest` 并审阅变更。
2. 手工合并需要的 `agent.py`、Prompt、测试、依赖或 Dockerfile 修改，保留已验证的业务代码。
3. 保留 `agent.yaml.source` 和 `.muye-generation.json` 记录的首次生成来源，补充相关测试并执行
   `agent validate` 与 Agent 本地测试。此时 `source_drift: true` 是开发者接管后的预期提示，不表示
   descriptor/provenance 基线失效。
4. 通过 CI 构建不可变镜像并在阶段 5 的 BuildRecord/Catalog 流程中发布。

若变更范围过大，使用新的 slug 与新的稳定 `agent_id` 创建第二个目录，保留旧 Agent 直到显式下线。不能以复制
目录、移动目录或修改 provenance 代替审阅和迁移。
