#### REVIEW-20260730-01：Milvus Collection 与 muye-data 配置的向量维度不一致

- 阶段：阶段 1
- 严重程度：高
- 状态：已解决（2026-07-30）
- 位置：`poc/phase1/milvus/muye-data.config.yaml:24`、`poc/phase1/milvus/verify_hybrid.py:30`、`poc/phase1/milvus/verify_hybrid.py:79`
- 触发条件：使用 PoC seed 工具创建 `phase1_product_handbook_v1`，随后按随附的 `muye-data.config.yaml` 启动检索服务。

#### REVIEW-20260730-02：生成源码与 provenance 可以使用互相矛盾的输入

- 阶段：阶段 1
- 严重程度：高
- 状态：已解决（2026-07-30）
- 位置：`poc/phase1/generator.py:36`、`poc/phase1/generator.py:52`、`poc/phase1/generator.py:80`、`poc/phase1/generator.py:173`

- 验证：回归测试覆盖 agent ID、resource revision、model alias 和 scope 值不一致，并断言目标目录未写入。

#### REVIEW-20260730-07：Dense scope 断言存在假阳性

- 阶段：阶段 1
- 严重程度：低
- 状态：已解决（2026-07-30）
- 位置：`poc/phase1/milvus/verify_hybrid.py:30`、`poc/phase1/milvus/verify_hybrid.py:143`、`poc/phase1/milvus/verify_hybrid.py:168`
- 触发条件：Dense 查询的 scope filter 被移除、拼错或后端忽略。
- 实际影响：scope 内外两条退款数据使用完全相同的 `[1, 0, 0, 0]` 向量，断言只检查第一名。无 filter 对照查询中，scope 内记录仍因插入顺序排第一，因此 Dense 测试可能错误通过。Sparse 对照查询会暴露问题，但不能证明 Dense 通道自身正确应用 filter。
- 修复建议：让 scope 外向量获得严格更高的未过滤分数，并同时断言全部返回项的 `knowledge_id`；为过滤前后结果增加显式对照断言。
- 修复：scope 外退款记录获得更高的未过滤 Dense 分数；验证器先断言未过滤 Dense 首位为该对照记录，再检查 Dense、Sparse 和 Hybrid 的每一个命中均属于固定 knowledge_id。
- 验证：本机 Milvus 重建验证通过；独立单元测试确认 scope 断言会拒绝任意 scope 外命中。

#### REVIEW-20260731-33：镜像引用不能把配置 checksum 伪装成 registry digest

- 阶段：阶段 5
- 严重程度：高
- 状态：已解决（2026-07-31，本阶段待提交）
- 位置：`tools/agent_catalog/lifecycle.py`、`tools/agent_catalog/generator.py`
- 触发条件：构建后用自定义 config/source checksum 拼接 `tag@sha256:...`，再交给 Compose 部署。
- 实际影响：`tag@digest` 的 digest 必须是 registry manifest digest；配置 checksum 不是可拉取镜像身份，Compose 会拒绝
  或解析到错误对象，BuildRecord 也不能证明实际运行镜像。
- 修复：阶段 5 从本机 Docker daemon 读取内容寻址 image ID，BuildRecord 和 Compose 均使用
  `sha256:<docker-image-id>`；deploy/rollback 前再次 `docker image inspect`，缺失或不一致即拒绝。registry 发布留给阶段 6。
- 验证：生命周期 fake-runner 测试覆盖 build 记录、deploy/rollback 前摘要复核和历史指针重放。

#### REVIEW-20260731-34：服务 token 可复用会破坏目标与调用方身份隔离

- 阶段：阶段 5
- 严重程度：高
- 状态：已解决（2026-07-31，本阶段待提交）
- 位置：`templates/agents/react-knowledge/v1/main.py.tmpl`、`control_server/main.py`、
  `agents/agent-main/config/settings.py`、`muye-data/src/auth.py`
- 触发条件：同一 Agent 复用 Main/Control/Data token，Control 复用 operator/main/health token，或两个 Agent 在同类映射中
  使用相同 token。
- 实际影响：获得低权限或其他目标凭据的调用方可能跨接口或跨 Agent 使用该值，服务身份不再绑定预期调用方向。
- 修复：生成 Agent 启动时要求三类 token 非空且互不相同；Control 要求自身三类 token 不同；Main、Control 和 Data 的
  per-Agent 映射拒绝空值、非法 agent_id 和重复 token。Compose 只引用 secret 环境变量，不写入明文。
- 验证：模板、Control、Main 和 Data 均有凭据复用负例；Control 内部路由还验证 operator/main/health 不能互换。

#### REVIEW-20260731-35：只做 Main 工具授权不能限制 SubAgent 直接读取 Data Resource

- 阶段：阶段 5
- 严重程度：高
- 状态：已解决（2026-07-31，本阶段待提交）
- 位置：`muye-data/src/auth.py`、`muye-data/src/api.py`、生成 Agent 模板
- 触发条件：持有任意 Data token 的 SubAgent 伪造 `agent_id`、部署 identity 或请求未声明 Resource。
- 实际影响：Main 的请求级 grant 只能限制模型工具，不能阻止被绕过的 SubAgent 直接访问其他 Agent 的知识资源。
- 修复：Data token 绑定稳定 agent_id；每次请求重新校验 active Catalog checksum、service/deployment/version、
  descriptor/source identity 和 `resource_bindings`。Catalog 无效、Agent 非 ACTIVE、身份漂移或 Resource 未声明均
  fail closed。
- 验证：Data 授权测试覆盖合法访问、跨 Resource、伪造 checksum、错误 token、DEGRADED 和损坏 Catalog。
