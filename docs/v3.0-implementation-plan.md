# Muye Multi-Agent Scaffold v3.0 完整实施计划

- 状态：实施中（阶段 0、阶段 1 已完成；阶段 2 实施中）
- 目标版本：v3.0
- 文档日期：2026-08-27
- 适用分支：`v3.0.x-dev`
- 主要部署形态：单机 Docker Compose

## 1. 背景与结论

v2.0/v2.1 已经走通资料解析、知识构建、检索评测、Agent 生成、MainAgent 编排、用户授权、对话、发布和回滚，但整体复杂度已经影响使用和交付：

1. Web 只覆盖状态、授权和对话，Agent 创建、审批、生成、测试及发布仍依赖 CLI、Git 文件和多个运行环境，用户无法从空白状态在 UI 内完成闭环。
2. 运行时采用接近零信任微服务的服务 Token 体系。Control、MainAgent、Gateway、Health、Data 和每个 SubAgent 分别维护凭据，与“仅 Gateway 对外、其余服务位于可信单机私有网络”的实际部署模型不匹配。
3. Gateway、Dashboard API、Control、MainAgent、LLM、Data、Channels 等常驻模块分别部署，配置和状态分散在数据库、多个 `.env`、Catalog、Snapshot 与生成的 Compose 文件中。
4. v2 的“生成源码后交由 Git 接管”适合开发者脚手架，但不适合由 UI 持续管理 Agent 生命周期。如果继续让 UI 调用 CLI、写源码或操作 Git，只会隐藏而不会消除双入口和状态分裂。

v3.0 采用以下核心方案：

- 将平台能力收敛为 `gateway`、`core`、`deployment-runner` 三个常驻业务部署单元。
- UI 首发只创建声明式知识 Agent，不接受任意 Python、Shell、依赖或镜像。
- 每个 Agent 保持独立容器，但共享一个固定 digest 的通用 `knowledge-agent-runtime` 镜像。
- Core API 是唯一业务入口和事实源；Web 与 CLI 均调用同一 API。
- 删除私有 Compose 网络内的平台间及 Agent 间 Token，只保留外部用户会话、用户-Agent grant 和真实外部系统凭据。
- Core 不挂载 Docker socket；受限 Runner 负责 Agent 容器生命周期。
- v2 Agent 不自动迁移，全部通过 v3 UI 人工重建、重新评测并逐个切换。

## 2. 目标、非目标与成功标准

### 2.1 目标

- 管理员无需终端，从 UI 完成 Agent 创建、资料上传、配置、审批、知识构建、评测、预览、授权、上线、停止和回滚。
- 单机生产环境只需维护一份平台配置，并通过一次 Compose 启动完成平台部署。
- 常驻业务服务由当前约七个收敛为三个，同时保持每个 Agent 的进程、资源和故障隔离。
- 业务状态、任务状态、Revision、授权、部署记录和审计记录统一进入 PostgreSQL。
- 所有长任务可观察、可取消、可恢复、可重试且具备幂等保证。
- 检索质量、citation、拒答边界、流式事件和用户授权能力不低于 v2。
- 通过固定 Runtime、网络隔离、只读文件系统和 Runner allowlist，限制声明式 Agent 的运行权限。

### 2.2 非目标

- v3.0 首发不支持任意代码 Agent、在线生成 Python、在线安装依赖或用户指定容器镜像。
- v3.0 首发不承诺 Kubernetes、多节点高可用、跨主机服务发现或零信任工作负载身份。
- v3.0 首发不自动导入 v2 生成目录、源码修改、BuildRecord 或 Catalog。
- v3.0 不允许 Core、Web 请求或模型输出直接执行 Docker、Shell、Git 或宿主机文件操作。
- v3.0 不引入复杂多级 RBAC。保留内置 Admin、普通用户和 `user_agent_grants`。

### 2.3 成功标准

- 在全新环境中，仅 Gateway 的 80/443 对宿主机和公网开放。
- 管理员可在 UI 中于 30 分钟内从一组有效资料创建并上线首个知识 Agent，不执行 CLI。
- 同一操作重复提交不会产生重复 Revision、Milvus Collection、Deployment 或容器。
- 发布失败不会影响当前 Active Revision；回滚不需要重新构建知识。
- Core 或 Runner 异常重启后，未完成任务能恢复或明确进入可重试失败态。
- v2/v3 固定评测集对比中，v3 的检索门禁、citation 正确率和拒答质量不得下降。

## 3. 总体架构

```text
Browser / API Client / CLI
            |
            v
        muye-gateway
    TLS / Static UI / Routing
            |
            v
         muye-core
  +-----------------------------+
  | Identity / Grants / Audit   |
  | Agent Studio / Revision     |
  | Jobs / Evaluation / Catalog |
  | MainAgent / LLM / Retrieval |
  | Channels / Chat / Citation  |
  +-----------------------------+
       |          |          |
       v          v          v
  PostgreSQL  Artifact    Milvus
              Storage
       ^
       |
 deployment-runner ---- Docker API
       |
       +--> agent-<id>-<revision> containers
             fixed knowledge-agent-runtime image
```

### 3.1 部署单元

| 部署单元 | 职责 | 对外端口 | 特权边界 |
| --- | --- | --- | --- |
| `gateway` | TLS、静态 Web、公开路由、限流和安全 Header | 80/443 | 不访问数据库、Artifact 或 Docker |
| `core` | 全部业务 API、身份、Agent Studio、MainAgent、LLM/Data、任务、审计和 Channel | 无 | 不挂载 Docker socket，不执行任意命令 |
| `deployment-runner` | 领取受限部署任务、创建/更新/停止 Agent 容器、健康检查 | 无 | 唯一可访问 Docker API 的业务进程 |
| `knowledge-agent-runtime` | 加载一个不可变 Revision Bundle，执行声明式知识 Agent | 无宿主机端口 | 非 root、只读、无 Shell/任意工具 |
| PostgreSQL | 平台事实状态、任务、授权、审计 | 无 | 独立数据库角色和备份策略 |
| Milvus | 不可变知识 Collection | 无 | 只在私有网络内访问 |
| Artifact Storage | 原始资料、解析产物、Bundle、评测报告 | 无 | 固定根目录或 S3-compatible 接口 |

### 3.2 v2 模块归并关系

| v2 模块 | v3 归属 | 处理方式 |
| --- | --- | --- |
| Nginx Gateway | `gateway` | 保留并更新 `/api/v3`、聊天 SSE 与 Web 路由 |
| Dashboard API | `core.operations` | 合并健康、拓扑与运行状态 API |
| Control Server | `core.identity`、`core.catalog`、`core.audit` | 合并身份、grant、Catalog 和审计事务 |
| Agent Main | `core.orchestration` | 作为 Core 内部模块，保留编排、熔断和流式协议 |
| muye-llm | `core.models` | 保留模型 alias、Chat/Embedding/Rerank 适配层 |
| muye-data | `core.retrieval` | 与构建/评测共用 Snapshot 和检索实现 |
| muye-channels | `core.channels` | 保持凭据加密和外部协议隔离，但不再独立进程 |
| Agent Generator | Revision Bundle Builder | 不再生成 Python 源码，只生成受 Schema 校验的声明式 Bundle |
| Agent Catalog CLI | `core.catalog` + Runner | Catalog 由数据库事务生成，部署由任务驱动 |

### 3.3 代码边界建议

Core 使用模块化单体，模块之间通过 Python 接口和领域事件协作，不通过本机 HTTP。建议目录为：

```text
muye_core/
├── api/                 # FastAPI 路由、认证依赖、错误映射
├── identity/            # 用户、会话、Admin、grant
├── agents/              # Agent、Draft、Revision、Bundle
├── knowledge/           # 解析、切分、Embedding、Milvus 发布
├── evaluation/          # 固定评测、门禁和报告
├── orchestration/       # MainAgent、工具投影、调用预算
├── runtime/             # Runtime 契约、Catalog、部署投影
├── jobs/                # Job、lease、事件、取消和恢复
├── channels/            # 微信等外部 Channel
├── audit/               # 不可变审计事件
├── models/              # LLM/Embedding/Rerank provider
├── retrieval/           # Dense/Keyword/Hybrid/Rerank
└── operations/          # 健康、就绪、指标和诊断

deployment_runner/
knowledge_agent_runtime/
web/
```

不得在第一阶段通过大规模移动代码开始重构。先建立 v3 契约和测试，再逐模块迁移，确保每次归并都可验证。

## 4. 领域模型与持久化

### 4.1 核心实体

| 实体 | 关键字段 | 不变量 |
| --- | --- | --- |
| `agents` | `id`、`slug`、`display_name`、`description`、`created_by`、`archived_at` | `id` 稳定；`slug` 全局唯一；不能通过 Revision 修改身份 |
| `agent_drafts` | `agent_id`、`base_revision_id`、`config_json`、`updated_by`、`version` | 每个 Agent 最多一个开放 Draft；可编辑；使用乐观锁；不能直接部署 |
| `source_assets` | `id`、`sha256`、`size`、`media_type`、`storage_key`、`parse_status` | 内容寻址；同内容复用；物理路径不由客户端提供 |
| `draft_sources` | `agent_id`、`asset_id`、`display_name`、`sort_order` | 只绑定已完成安全检查的 Asset |
| `agent_revisions` | `id`、`agent_id`、`revision_number`、`checksum`、`spec_json`、`status` | 创建后不可变；checksum 覆盖全部逻辑输入 |
| `revision_sources` | `revision_id`、`asset_id`、`asset_sha256` | Revision 冻结后不可修改 |
| `revision_approvals` | `revision_id`、`revision_checksum`、`approved_by`、`approved_at` | checksum 变化必须重新审批 |
| `knowledge_builds` | `id`、`revision_id`、`collection_name`、`document_set_checksum`、`status` | 一个成功 Build 对应一个不可变 Collection |
| `evaluation_runs` | `id`、`revision_id`、`build_id`、`report_key`、`metrics_json`、`passed` | 只针对固定 Build；失败不得发布 |
| `revision_bundles` | `revision_id`、`bundle_checksum`、`storage_key`、`runtime_contract_version` | Bundle 不含密钥、URL 和物理数据库凭据 |
| `deployments` | `id`、`agent_id`、`revision_id`、`runtime_digest`、`status`、`container_ref` | 同一 Agent 最多一个 Active Deployment |
| `deployment_routes` | `agent_id`、`active_deployment_id`、`generation` | 原子切换；MainAgent 只读取 Active 路由 |
| `jobs` | `id`、`type`、`subject_id`、`idempotency_key`、`status`、`lease_owner`、`lease_until` | 同类型和幂等键唯一；状态单向转换 |
| `job_events` | `job_id`、`sequence`、`event_type`、`payload_json` | sequence 单调递增；事件不可更新 |
| `audit_events` | `actor_id`、`action`、`target_type`、`target_id`、`request_id`、`details_json` | 追加写；不得保存 Token 或完整资料正文 |

现有 `control_users`、`control_sessions` 和 `user_agent_grants` 数据语义保留。实施时可通过迁移重命名，但不得改变“新用户默认无 Agent 权限”和“授权绑定稳定 Agent ID”的行为。

### 4.2 Revision Spec

`AgentRevisionSpecV1` 至少包含：

```json
{
  "schema_version": "muye.ai/agent-revision/v1",
  "agent_id": "agent_hotel_employee",
  "display_name": "酒店员工助手",
  "objective": "根据已批准资料回答员工制度问题并提供引用。",
  "instructions": "...",
  "prohibited_actions": ["..."],
  "examples": ["..."],
  "model": {
    "chat_alias": "default-chat",
    "embedding_alias": "default-embedding",
    "temperature": 0.2
  },
  "retrieval": {
    "pipeline": "hybrid",
    "top_k": 8,
    "rerank_alias": null,
    "minimum_score": 0.0
  },
  "budgets": {
    "output_tokens": 4096,
    "tool_calls": 4,
    "timeout_seconds": 60
  },
  "source_assets": [
    {"asset_id": "asset_...", "sha256": "...", "display_name": "员工手册.md"}
  ],
  "evaluation": {
    "cases": [{"question": "...", "expected_source_asset_ids": ["asset_..."]}],
    "minimum_pass_rate": 0.8,
    "citation_required": true
  }
}
```

约束：

- 服务端维护所有枚举、数字上下限和模型 alias 白名单，不能信任 UI 校验。
- Prompt 使用简体中文明确角色、资料边界、禁止行为、输出格式、citation 要求和空召回行为。
- Spec 不允许 URL、文件路径、环境变量名、密钥形态、容器参数、模板代码或可执行表达式。
- LLM 生成的 Profile 和评测题只作为 Proposal，必须通过 Schema 校验并由管理员审批。
- Revision checksum 使用规范 JSON 序列化后计算 SHA-256，不包含时间戳和数据库 ID 之外的运行态字段。

### 4.3 状态机

Revision 状态：

```text
DRAFT -> REVIEW_REQUIRED -> APPROVED -> BUILDING -> EVALUATING -> READY
                         \-> REJECTED       \-> FAILED        \-> FAILED
```

Deployment 状态：

```text
PENDING -> DEPLOYING -> VERIFYING -> ACTIVE -> DRAINING -> STOPPED
                \-> FAILED          |
                                     +-> ROLLING_BACK -> ACTIVE
```

Job 状态：

```text
PENDING -> RUNNING -> SUCCEEDED
              |  \-> FAILED
              +----> CANCEL_REQUESTED -> CANCELLED
```

每个转换由领域服务显式校验。API、Worker 和 Runner 不得直接更新任意状态字符串。失败必须记录稳定错误码、可安全展示的信息和内部关联 ID。

### 4.4 Artifact 布局

本地 Compose 默认使用固定根目录 `/var/lib/muye/artifacts`：

```text
artifacts/
├── assets/<sha256-prefix>/<sha256>
├── parsed/<asset-sha256>/<parser-version>/document.json
├── evaluations/<revision-id>/<evaluation-id>/report.json
└── bundles/<agent-id>/<revision-id>/<bundle-checksum>.tar.zst
```

- 数据库只保存 storage key，不保存任意绝对路径。
- 所有读取均在拼接后执行根目录约束、普通文件检查和 symlink 拒绝。
- Bundle 先写临时文件，完成 checksum 与内容校验后原子发布。
- 上传资料、解析结果和 Bundle 分别设置大小上限和保留策略。
- 删除 Agent 默认只归档元数据；Artifact 和 Collection 由单独 GC 任务在确认无 Revision、Deployment 和审计引用后清理。

## 5. Core API 设计

### 5.1 通用约定

- 公开 API 前缀为 `/api/v3`，JSON 字段使用 `snake_case`。
- 所有写请求接受 `Idempotency-Key`；服务端保存请求主体 checksum 和最终结果。
- 响应包含 `request_id`；长任务返回 `202 Accepted`、`job_id` 和资源链接。
- 乐观更新使用 `If-Match` 或显式 `version`，冲突返回 `409`。
- 错误统一为 `{code, message, request_id, details?}`；`details` 不返回内部 URL、SQL、路径、凭据或异常正文。
- 分页统一使用不透明 cursor，默认 50、最大 200。
- 所有时间为 UTC RFC 3339；数据库使用带时区时间类型。

### 5.2 Agent Studio API

| 方法与路径 | 用途 | 关键行为 |
| --- | --- | --- |
| `POST /agents` | 创建 Agent 和初始 Draft | 校验 slug；记录审计；返回 Draft version |
| `GET /agents` | 查询 Agent 列表 | 支持状态、关键字和分页 |
| `GET /agents/{agent_id}` | Agent 聚合详情 | 返回 Draft、最新 Revision、Active Deployment 和授权摘要 |
| `POST /agents/{agent_id}/draft` | 从指定 Revision 创建更新草稿 | 默认基于 Active Revision；已有开放 Draft 时返回 `409` |
| `PATCH /agents/{agent_id}/draft` | 更新草稿配置 | 乐观锁；服务端完整校验 |
| `DELETE /agents/{agent_id}/draft` | 放弃开放 Draft | 不影响任何已冻结 Revision 或线上 Deployment |
| `GET /agents/{agent_id}/draft/impact` | 分析草稿变更影响 | 返回复用、增量处理、全量重建及必须重跑的评测项 |
| `POST /agents/{agent_id}/sources` | 上传资料 | multipart 流式落盘；限制类型、大小和数量 |
| `DELETE /agents/{agent_id}/sources/{asset_id}` | 从 Draft 移除资料 | 不立即物理删除共享 Asset |
| `POST /agents/{agent_id}/profile-proposals` | 生成 Profile/评测 Proposal | 异步任务；模型输出必须结构化校验 |
| `POST /agents/{agent_id}/revisions` | 冻结 Draft | 创建不可变 Revision 和 checksum |
| `POST /revisions/{revision_id}/approve` | 审批 Revision | 必须提交当前 checksum；Admin 操作 |
| `POST /revisions/{revision_id}/build` | 构建、评测和 Bundle | 只允许 APPROVED；返回 Job |
| `GET /revisions/{revision_id}` | Revision 详情 | 返回构建、评测和部署历史 |
| `GET /revisions/{revision_id}/evaluation` | 评测报告 | 返回指标和经裁剪的命中证据 |

### 5.3 部署 API

| 方法与路径 | 用途 | 关键行为 |
| --- | --- | --- |
| `POST /revisions/{revision_id}/deploy` | 上线 READY Revision | 创建 Deployment Job；不能接受镜像或 Docker 参数 |
| `GET /deployments/{deployment_id}` | 查询部署 | 返回状态、版本、健康与稳定错误码 |
| `POST /deployments/{deployment_id}/stop` | 停止 Agent | 先撤销路由，再排空并停止容器 |
| `POST /agents/{agent_id}/rollback` | 回滚 | 目标必须是该 Agent 的历史 SUCCEEDED Deployment |
| `GET /agents/{agent_id}/deployments` | 部署历史 | 支持分页；不展示内部容器地址 |
| `POST /agents/{agent_id}/archive` | 逻辑移除 Agent | 阻止新调用和写操作，撤销路由与 grant，停止容器后归档 |
| `POST /agents/{agent_id}/restore` | 恢复已归档 Agent | 只恢复可管理状态，不自动恢复 grant 或部署 |

### 5.4 Job 与流式 API

- `GET /jobs/{job_id}` 返回当前阶段、进度、开始/结束时间、错误码和是否可取消/重试。
- `POST /jobs/{job_id}/cancel` 只设置取消请求，不假装同步终止下游操作。
- `POST /jobs/{job_id}/retry` 仅为允许重试的失败创建新 Attempt，并复用原始幂等输入。
- `GET /jobs/{job_id}/events` 使用 SSE，事件顺序为 `snapshot`、`progress`/`log`/`artifact`、`completed` 或 `failed`。
- SSE 支持 `Last-Event-ID` 恢复、15 秒心跳和显式 `stream_end`；浏览器断开不自动取消后台任务。
- `POST /chat/stream` 保留 v2 的 `session_start -> block/tool/thinking -> done -> session_end` 语义，并增加协议版本字段。

### 5.5 CLI 定位

v3 CLI 是 API 薄客户端，保留自动化与故障恢复能力：

```bash
./scripts/muye.sh agent create --file agent.json
./scripts/muye.sh agent upload <agent-id> <files...>
./scripts/muye.sh agent revise <agent-id>
./scripts/muye.sh agent approve <revision-id> --checksum <sha256>
./scripts/muye.sh agent build <revision-id> --wait
./scripts/muye.sh agent deploy <revision-id> --wait
./scripts/muye.sh agent rollback <agent-id> --deployment <id> --wait
./scripts/muye.sh agent stop <agent-id> --wait
./scripts/muye.sh agent archive <agent-id> --wait
./scripts/muye.sh agent restore <agent-id>
```

CLI 不得直接导入 Core 内部 Service、不写数据库、不生成 Compose、不访问 Milvus、不操作 Docker，也不维护第二套校验逻辑。

## 6. UI 实施

### 6.1 信息架构

新增以下工作视图：

- Agent 列表：名称、Draft/Revision 状态、Active 版本、健康、最近操作和快捷入口。
- 创建/编辑页：基本信息、行为边界、模型与预算、检索设置。
- 资料页：拖放上传、解析状态、内容 hash、失败原因和移除操作。
- 审阅页：Profile、Prompt、评测问题、资料清单和 Revision checksum。
- 构建评测页：阶段进度、可取消状态、指标、失败案例、citation 和检索命中详情。
- 预览页：独立会话，对比回答、工具过程、citation 与原始 SSE。
- 发布页：Revision 摘要、授权选择、发布确认和实时部署进度。
- 运行详情页：Active Revision、健康、延迟、token、错误、部署历史、停止与回滚。
- 审计页：按 Agent、用户、动作、时间筛选。

### 6.2 交互约束

- 使用步骤导航表达创建阶段，但服务端状态是唯一事实源，前端不得仅依赖本地步骤状态。
- 上传使用流式进度，并支持单文件重试；同 hash 文件提示复用。
- 长任务离开页面后继续运行，返回页面时从 Job snapshot 和事件序号恢复。
- 破坏性操作使用确认对话框，明确目标 Agent、Revision 和影响；按钮提交后防重复点击。
- 评测未通过时禁用发布，并展示服务端门禁原因，前端不能提供绕过入口。
- 回滚只列出服务端确认可回滚的历史 Deployment。
- SSE 断线显示重连状态；任务已完成时通过快照补齐最终结果。
- 所有页面覆盖空数据、加载、部分失败、权限不足、冲突、后端不可用和会话过期状态。

### 6.3 前端状态与测试

- API DTO 与服务端 OpenAPI 生成的 TypeScript 类型保持一致，禁止手写漂移的重复类型。
- Pinia 只保存页面需要的缓存和 UI 状态，不作为任务或部署事实源。
- 上传、SSE 和聊天请求使用 `AbortController`；取消浏览器请求与取消后台 Job 明确区分。
- 组件测试覆盖校验、状态切换、失败展示和幂等按钮。
- Playwright E2E 覆盖从创建到上线、评测失败、部署失败、停止和回滚。

### 6.4 Agent 生命周期操作流程

Agent 身份、Revision、Knowledge Build 和 Deployment 是四个不同层次：

| 层次 | 版本规则 | 生命周期含义 |
| --- | --- | --- |
| Agent | 稳定 `agent_id`，创建后不变 | 用户 grant、审计和所有历史版本的归属主体 |
| Revision | 按 Agent 单调递增，创建后不可变 | Prompt、资料、模型、检索和评测配置的完整逻辑快照 |
| Knowledge Build | 每次构建尝试使用独立 Build ID | Revision 对应的解析、向量和不可变 Collection 结果 |
| Deployment | 每次上线、重新部署或回滚使用独立 Deployment ID | 某个 Revision 在某个 Runtime digest 上的实际运行记录 |

Agent 列表中的 `DRAFT_ONLY`、`READY`、`ACTIVE`、`STOPPED`、`ARCHIVING` 和 `ARCHIVED` 是上述事实计算出的展示状态，不再维护一套可与 Revision/Deployment 冲突的独立状态字段。

#### 6.4.1 新增 Agent

从零创建 Agent 的标准流程为：

```text
创建 Agent/初始 Draft
  -> 配置目标、Prompt、模型、检索和预算
  -> 上传并解析资料
  -> 生成并审阅 Profile/评测 Proposal
  -> 冻结 Revision 1
  -> checksum 审批
  -> 构建知识与执行评测
  -> 生成 Bundle 并进入 READY
  -> 预览对话
  -> 配置用户 grant
  -> 蓝绿部署并进入 ACTIVE
```

实施规则：

1. `POST /agents` 在同一数据库事务中创建稳定 `agent_id` 和初始 Draft。`slug` 全局唯一且永久保留，归档后也不能被新 Agent 复用。
2. 初始 Draft 至少包含目标、禁止行为、一个有效模型 alias、一份资料和一个评测问题，缺失时不能冻结 Revision。
3. 上传成功只表示 Asset 已安全落盘，不表示已进入线上知识；只有冻结 Revision 时绑定的资料才属于该版本。
4. Revision 1 构建或评测失败时，Agent 仍为 `DRAFT_ONLY` 或失败 Revision，不创建运行路由，也不影响其他 Agent。
5. 只有 `READY` Revision 可以部署。Runner 完成 readiness 与 smoke 后，Core 才创建 Active Route。
6. grant 始终绑定稳定 Agent ID，而不是 Revision 或 Deployment。Agent 尚未 Active 时 grant 可以预先配置，但调用仍被拒绝。
7. 创建、上传、冻结、审批、构建、授权和部署分别记录审计事件；同一幂等请求不得生成两个 Agent 或 Revision。

#### 6.4.2 更新 Agent

更新不能直接修改 Active Revision。管理员必须从一个明确的 `base_revision_id` 创建开放 Draft；默认基于当前 Active Revision。v3.0 每个 Agent 同时最多存在一个开放 Draft，以避免分支版本、并行审批和版本合并带来的复杂度。

```text
Active Revision N
  -> 创建基于 N 的 Draft
  -> 修改配置或资料
  -> 查看变更影响分析
  -> 冻结 Revision N+1
  -> 审批、构建、评测和预览
  -> 蓝绿发布 Revision N+1
  -> 保留 Revision N 作为回滚点
```

Core 根据 Asset hash 和配置差异生成确定性的 Change Impact：

| 变更类型 | 可复用内容 | 必须执行 |
| --- | --- | --- |
| 仅追加文档 | 旧资料解析结果、Chunk、Embedding 和评测用例 | 只解析/Embedding 新文档；生成新的完整 Collection；执行新增评测和历史回归 |
| 删除文档 | 未删除资料的解析、Chunk 和 Embedding | 新 Collection 排除被删除资料；重跑完整检索与 citation 评测 |
| 替换文档 | 未变化资料的全部缓存 | 只处理新 hash 文档；新 Collection 使用保留资料与替换资料；重跑完整评测 |
| 只修改 Prompt、目标或禁止行为 | 原 Knowledge Build 和 Collection | 生成新 Bundle；重跑回答、拒答、提示注入和 citation 回归 |
| 修改 Chat 模型或输出预算 | 原 Knowledge Build 和 Collection | 校验新模型能力；重跑回答质量、超时和 token 预算评测 |
| 修改 `top_k`、阈值、Hybrid 权重或 Rerank | 原文档解析和 Embedding | 重跑完整检索评测；配置兼容时复用 Collection |
| 修改 Embedding 模型、向量维度、解析器或切分规则 | 仅复用原始 Asset | 全部重新解析或切分、Embedding，创建新 Collection 并完整评测 |

仅追加新文档时采用增量快速路径，但版本仍然保持完整和不可变：

```text
Revision 1 Collection = 旧向量 A + B
Revision 2 Collection = 复用向量 A + B + 新向量 C + D
```

- 旧文档不重新解析，也不再次调用 Embedding；其缓存键必须同时匹配 Asset SHA-256、解析器版本、切分策略、Embedding alias 和实际模型 revision。
- Revision 2 仍创建新的完整不可变 Collection。旧向量从已验证缓存或上一 Build 批量写入，新向量增量加入，避免基础 Collection 与多层增量 Collection 带来的跨层召回、去重和压缩复杂度。
- 新资料必须补充针对新增知识的评测问题；原有核心评测集必须回放，防止新增内容稀释排序或引入矛盾答案。
- 如果追加资料与旧资料内容冲突，评测报告必须暴露冲突命中。系统不能凭上传时间默认判定新资料优先；需要管理员在资料或 Prompt 中明确解决后再发布。
- Revision N+1 发布失败时，Revision N 继续服务。发布成功后，进行中的旧请求在 Revision N 完成，新请求使用 Revision N+1。
- 每次回答记录实际 `revision_id`、`build_id` 和 citation。历史 citation 在保留期内继续按原 Revision 解析。
- 放弃 Draft 只删除草稿绑定，不删除 base Revision、已上传的共享 Asset 或线上 Deployment。

#### 6.4.3 停止、移除与恢复 Agent

UI 必须区分“停止运行”和“移除 Agent”，不得使用一个含糊的删除按钮：

| 操作 | 是否可逆 | 路由和容器 | grant | 历史数据 |
| --- | --- | --- | --- | --- |
| 停止 | 是 | 立即撤销新请求路由，排空后停止容器 | 保留但暂时无效 | 全部保留，可重新部署 |
| 移除（归档） | 是 | 撤销路由并停止全部活动容器 | 主动撤销，恢复后不自动还原 | Revision、Build、Deployment、citation 和审计按保留策略保存 |
| 物理清理 | 通常不可逆 | 不适用 | 不适用 | 仅由保留策略驱动的后台 GC 执行 |

停止流程：

1. Admin 提交幂等停止请求。
2. Core 在事务中删除 Active Route，使新请求立即返回稳定的 `AGENT_INACTIVE` 错误。
3. 已进入 Runtime 的请求允许在排空超时内完成；超时后 Runner 执行取消和停止。
4. Deployment 进入 `STOPPED`，Agent 展示为 `STOPPED`。Revision 和 grant 不变。
5. 后续可重新部署任意仍满足兼容性和保留要求的 READY Revision。

移除流程采用逻辑归档：

1. Admin 在 UI 中确认 Agent 名称和影响范围，Core 创建 `AGENT_ARCHIVE` Job，并将 Agent 置为 `ARCHIVING`。从此拒绝新 Draft、构建、部署、授权和聊天请求。
2. 对正在运行的构建或部署请求取消；不可立即取消的外部操作等待 checkpoint 后终止。
3. Core 原子撤销 Active Route 和全部 `user_agent_grants`，并在审计事件中记录受影响用户和版本引用。
4. Runner 排空并停止该 Agent 的全部活动容器；失败时 Job 保持可重试，不得假装归档完成。
5. 无活动容器后写入 `archived_at`，Agent 默认从普通列表隐藏，但管理员可在归档视图查询。
6. Revision、Build、Evaluation、Bundle、Deployment、聊天版本引用和审计记录不立即删除，以支持调查和保留期内恢复。

恢复流程：

1. Admin 执行 `restore`，清除 `archived_at` 并重新开放 Draft/部署操作。
2. 恢复不会自动重建用户 grant，也不会自动启动旧 Deployment，避免归档期间已失效的授权静默恢复。
3. Admin 必须选择一个仍可用的 READY Revision 重新部署，并重新确认用户授权。
4. 如果 Bundle、Collection、Runtime digest 或契约版本已超过保留/兼容范围，必须创建新 Revision 并重新构建，不能绕过完整性检查。

物理清理由后台 GC 执行，不作为普通 Agent Studio 操作。GC 只有在满足以下条件时才能删除对象：不存在 Active/可回滚 Deployment 引用、超过配置的回滚和 citation 保留期、没有 Revision 或共享 Asset 引用，并且已生成可审计的清理计划。`agent_id`、`slug` 墓碑和最小审计记录永久保留，防止旧引用被错误绑定到新 Agent。

## 7. 知识构建、评测与 Runtime

### 7.1 构建 Pipeline

固定阶段如下：

```text
validate_revision
  -> parse_assets
  -> chunk_documents
  -> embed_chunks
  -> publish_candidate_collection
  -> evaluate_dense_keyword_hybrid
  -> publish_evaluation_report
  -> build_revision_bundle
  -> mark_ready
```

- 每个阶段读取不可变 Revision，不读取当前 Draft。
- `asset_sha256 + parser_version` 决定解析缓存键；Embedding 缓存键额外包含模型 alias、实际 provider revision 和 chunk checksum。
- Collection 名由 Revision/Build ID 派生，客户端不可指定。
- 批量写入使用确定性主键；重试时 upsert 或验证已写结果，不重复计数。
- 仅对限流、连接失败和超时等可恢复错误执行有上限的指数退避；Schema、权限、资料漂移和评测失败不自动重试。
- 构建取消后标记候选资源，交给 GC 延迟清理；不得删除 Active Revision 使用的 Collection。

### 7.2 评测门禁

- 至少执行 Dense、Keyword 和 Hybrid 三种检索评测，并记录每题命中、排序和 citation 证据。
- 固定记录 embedding alias/revision、rerank alias/revision、pipeline 参数和文档集合 checksum。
- 默认门禁为 Revision Spec 声明的 `minimum_pass_rate` 和 `citation_required`，其允许范围由平台配置限制。
- 空召回、低于阈值、无可信 citation 时必须拒答或声明无法从资料确认，不允许回退到模型常识并伪装为资料结论。
- 外部资料视为不可信内容，解析与 Prompt 组装时标记资料边界，防止资料中的提示注入修改系统规则或工具权限。
- 评测报告保存必要证据片段，但 UI、日志和审计不得无界复制完整知识正文。

### 7.3 Runtime Bundle

Bundle 至少包含：

```text
bundle/
├── manifest.json           # contract version、checksum、agent/revision identity
├── revision.json           # AgentRevisionSpecV1
├── resource-snapshot.json  # 逻辑资源到不可变 Collection 的映射
└── evaluation-summary.json # 门禁结果和评测引用
```

- `bundle_checksum` 是包含 `manifest.json`（排除其自身 `bundle_checksum` 字段）及三个固定成员内容 SHA-256 的规范 JSON SHA-256；它不依赖 tar/zstd 字节、文件时间戳或成员顺序。Runtime 在读取任意成员前重新计算并验证该值。
- Runtime 启动时先验证 Bundle checksum、Schema、Agent ID、Revision ID 和 Runtime contract version。
- Runtime 只从平台注入固定 Core 地址、部署身份和 Bundle 挂载点；不接受用户请求覆盖。
- Runtime 提供 `/health`、`/ready`、`/capabilities`、`/invoke`、`/invoke/stream` 和 `/cancel` 内部接口。
- 每次调用限制总超时、模型输出 token、工具调用次数、检索 top-k、并发和上下文长度。
- 工具集合固定为受控只读检索；v3.0 不提供任意 HTTP、文件、数据库或 Shell 工具。
- Runtime 日志只记录 request/deployment/revision ID、耗时、token、工具次数和错误分类。

## 8. 鉴权与安全边界

### 8.1 保留的安全机制

- Gateway/Core 用户登录、短期 Access Token、HttpOnly Refresh Cookie 和退出撤销。
- Admin 管理权限和普通用户权限分离。
- `user_agent_grants(user_id, agent_id)`；新用户默认无 grant，调用前实时复核。
- Gateway 丢弃客户端伪造的内部身份 Header，Core 从已验证会话构建 CallerContext。
- LLM、Embedding、Rerank、Milvus、PostgreSQL、Channel 等真实外部或基础设施凭据继续由环境或 Secret 管理。

### 8.2 删除的内部 Token

- 删除 Control operator/main/health/gateway Token。
- 删除每个 Agent 的 Main、Control 和 Data Token。
- 删除内部 Token JSON 映射、Token 唯一性校验、轮换脚本和相关 `.env` 项。
- Core 内部模块调用改为进程内接口；Core 与 Agent Runtime 的 HTTP 调用依赖私有网络和固定部署拓扑。

取消内部 Token 只适用于以下前提：

1. 单机可信 Docker 环境，只有管理员可以启动容器或加入内部网络。
2. 仅 Gateway 发布宿主端口，Agent、Core、Runner、数据库和 Milvus 均不 publish port。
3. Agent Runtime 是固定、受审计的声明式镜像，不能运行用户代码或任意工具。
4. Runner 严格限制镜像、命令、挂载、网络和资源参数。

一旦支持自定义代码 Agent、第三方容器、跨主机部署或非可信工作负载，必须先引入 mTLS 或工作负载身份，不得继续将内部网络视为充分鉴权。

### 8.3 容器加固

- Gateway、Core、Runner 和 Runtime 均以非 root 用户运行；基础镜像固定 digest。
- Runtime 使用 `read_only: true`、`no-new-privileges`、`cap_drop: [ALL]` 和受限 tmpfs。
- 禁止 privileged、host network、host PID/IPC、设备映射和任意 host path。
- Agent 容器只加入 `agent-runtime` 网络；不能加入 Runner 管理网络或访问 Docker API。
- 通过网络规则限制 Agent 只访问 Core 的 Runtime API；不能直接访问 PostgreSQL、Milvus或管理 API。
- 上传文件执行扩展名、MIME、magic bytes、大小和压缩炸弹检查；解析器进程设置时间和内存限制。
- 构建 SBOM，执行依赖、镜像和许可证扫描；发布证据绑定 Runtime digest 与 Bundle checksum。

## 9. Deployment Runner

### 9.1 任务领取

- Runner 使用独立 PostgreSQL 角色，只能读取 Deployment Job、写 Deployment 状态和追加 JobEvent。
- 使用 `SELECT ... FOR UPDATE SKIP LOCKED` 领取任务，并写入有期限的 lease。
- Runner 定期续租；失去 lease 后必须停止后续状态写入。
- lease 到期的任务可被其他 Runner 恢复，但每一步先检查 Docker 中的确定性 label，避免重复容器。
- 容器 label 至少包含 `muye.managed=true`、Agent ID、Revision ID、Deployment ID、Bundle checksum 和 Runtime digest。

### 9.2 Runner 输入 allowlist

Runner 只接受 Core 已持久化并签入任务的以下字段：

- `deployment_id`
- `agent_id`
- `revision_id`
- 平台配置中的 `runtime_image_digest`
- 已验证的 `bundle_storage_key` 与 `bundle_checksum`
- 受平台上下限约束的 CPU、内存和并发档位
- 固定网络名和只读挂载目标

Runner 拒绝 API 或数据库任务中出现的任意 image、command、entrypoint、host path、port publish、environment map、privileged、device、capability 或 network override。

### 9.3 蓝绿发布

1. Core 创建 `PENDING` Deployment 和幂等 Runner Job。
2. Runner 验证 Runtime digest、Bundle、目标网络和资源限制。
3. Runner 创建候选容器，不修改当前 Active Route。
4. 等待 `/ready`，使用固定测试请求执行 capabilities 与 invoke smoke。
5. Runner 将候选标记为 `VERIFYING`，Core 在数据库事务中切换 `deployment_routes`。
6. MainAgent 读取新 generation，并将新请求发往候选容器。
7. 旧容器进入 `DRAINING`，等待已有请求完成或到达排空超时。
8. Runner 停止旧容器，候选 Deployment 进入 `ACTIVE`。

任一步失败都将候选标记为 `FAILED`，停止候选容器并保持旧 Active Route。不得因清理失败覆盖最初失败原因。

### 9.4 回滚与一致性修复

- 回滚目标必须属于同一 Agent，且曾通过 readiness/smoke 并拥有完整 Bundle。
- 若旧容器仍存在且校验一致，可重新启用；否则从历史 Deployment 的 Runtime digest 和 Bundle 重建。
- 切换路由与普通发布使用同一原子流程。
- Runner 启动时执行 reconcile：比较数据库期望状态与带 `muye.managed=true` label 的实际容器。
- reconcile 可启动缺失的期望容器、清理已停止 Deployment 的孤儿容器，但不得自动删除无法归属或 checksum 不匹配的容器；此类情况进入告警等待人工处理。

## 10. 配置、部署与运维

### 10.1 配置收敛

生产环境只维护一个平台 `.env` 或等价 Secret 注入，按前缀分组：

- `MUYE_CORE_*`：监听、数据库、Artifact、任务与日志。
- `MUYE_MODEL_*`：模型 provider、alias 和凭据。
- `MUYE_MILVUS_*`：Milvus 连接。
- `MUYE_GATEWAY_*`：TLS、公开域名、限流。
- `MUYE_RUNNER_*`：固定 Runtime digest、网络和资源档位。
- `MUYE_CHANNEL_*`：外部 Channel 配置与加密密钥。

禁止重复表达同一配置；例如模型 alias 注册表只由 Core 加载，Runtime 从 Revision 引用 alias，不重复配置 provider 凭据。

### 10.2 Compose 拓扑

使用三个网络：

- `public`：仅 Gateway 可加入并发布端口。
- `core-internal`：Gateway、Core、PostgreSQL、Milvus 和 Runner 的必要通信。
- `agent-runtime`：Core 与 Agent Runtime 通信，Agent 无法访问数据库和 Docker API。

Runner 的 Docker API 访问优先采用 rootless Docker socket。若目标环境只能使用 rootful Docker socket，必须在部署说明中标记 Runner 为宿主机高权限边界，限制镜像来源和主机管理员权限。

### 10.3 健康与可观测性

- `/health` 只表示进程存活；`/ready` 验证数据库、Artifact 和必要启动状态。
- 指标至少包含 API 延迟/错误、Job 队列长度/耗时、构建阶段、模型 token/延迟、检索延迟/空召回、Agent 调用、部署成功率和容器健康。
- 每个请求贯穿 `request_id`；异步链路同时记录 `job_id`、`revision_id` 和 `deployment_id`。
- 错误分类至少区分校验、认证、授权、冲突、限流、模型拒绝、内容过滤、模型超时、模型协议错误、检索不可用、评测未通过、部署失败和依赖不可用。
- 日志默认 JSON，禁止记录密码、Token、Cookie、模型 provider 密钥、Channel 凭据和完整资料正文。

### 10.4 备份恢复

- PostgreSQL、Artifact Storage 和 Milvus 必须作为同一恢复点管理，并保存 Runtime image digest 可获取性证明。
- 每次正式发布前执行隔离恢复演练，验证 Agent、Revision、Build、Evaluation、Deployment、grant 和审计记录。
- 恢复后 Runner 先进入 reconcile-only 模式，核对数据库和容器，再允许部署写操作。
- Artifact 或 Collection 缺失时，相应 Revision 标记为不可部署，不能静默重建后沿用旧 checksum。

## 12. 测试与质量保障

### 12.1 单元与契约测试

- Revision Schema、checksum、非法配置和 Prompt 边界。
- Agent 单开放 Draft、Revision 单调版本、Change Impact 和 slug 墓碑规则。
- 状态机所有允许/拒绝转换。
- Job lease、续租、过期、取消、重试和幂等键冲突。
- 模型正常、拒绝、过滤、限流、超时、无效 JSON 和协议错误。
- Dense/Keyword/Hybrid、空召回、低分、rerank 失败和 citation 生成。
- Bundle 路径、checksum、Schema 和 contract version。
- Runner allowlist 和 Docker 参数构造。
- Session、Admin、grant、撤权和审计脱敏。

### 12.2 集成测试

- PostgreSQL 事务、迁移升级/回滚和并发冲突。
- Artifact 原子写入、共享 Asset、损坏和磁盘不足。
- Milvus 部分写入、重试、候选清理和 Active Collection 保护。
- Job Worker/Core/Runner 分别在各阶段崩溃后的恢复。
- Runtime 与 Core 的 invoke、stream、cancel、readiness 和 route generation。
- Gateway 登录、Refresh Cookie、SSE、上传限制和公开路由白名单。

### 12.3 E2E 场景

1. 全新管理员创建用户和 Agent，上传资料，审批、评测、预览、上线并授权。
2. 普通用户只看到获授权 Agent，撤权后下一次调用立即失败。
3. 修改 Draft 不影响已上线 Revision；创建新 Revision 后可蓝绿升级。
4. 评测未通过时无法部署，修正资料后以新 Revision 重新执行。
5. 新版本 readiness 失败，旧版本继续服务。
6. 新版本上线后回滚到上一版本，路由与 citation 保持正确。
7. 浏览器在构建、部署和聊天 SSE 中断后恢复。
8. Core、Runner 和 Docker 分别重启，系统最终收敛到数据库期望状态。
9. 恶意上传、提示注入、伪造身份、跨 Agent citation 和 Docker 参数注入均失败。
10. 仅追加新文档时旧解析与 Embedding 缓存被复用，新旧知识均通过回归评测，并可回滚到旧 Revision。
11. 停止 Agent 后可重新部署；归档后路由与 grant 被撤销；恢复后不会自动恢复部署和授权。
12. GC 不删除仍被 Revision、Deployment、历史 citation 或共享 Asset 引用的对象。

### 12.4 非功能测试

- 并发：按目标机器定义 Core 请求、构建 Job 和 Agent 调用并发基线。
- 性能：记录 P50/P95/P99 API、首 token、完整回答、检索和部署耗时。
- 稳定性：执行至少 24 小时混合聊天、构建和部署耐久测试。
- 安全：依赖/镜像扫描、容器配置审计、端口扫描、网络访问矩阵和备份泄露检查。
- 容量：验证最大单文件、总资料、chunk 数、Agent 数和 Artifact 磁盘阈值。

## 13. 迁移与回退策略

### 13.1 v2 Agent 人工重建

每个 Agent 使用迁移清单记录：

- v2 Agent ID、负责人和当前用户 grant。
- 源资料的确认版本与 checksum。
- Prompt、目标、禁止行为、模型和预算的人工录入结果。
- v3 Revision checksum、Build、Evaluation 和 Deployment ID。
- v2/v3 对比评测结果与业务验收人。
- 切流时间、观察窗口和最终下线确认。

存在 `source_drift` 的 v2 Agent 不尝试自动解释或迁移源码行为。如果其中包含声明式 Runtime 无法表达的业务逻辑，该 Agent 暂留 v2，或从 v3.0 范围剔除并进入未来自定义 Agent 设计，不能通过隐藏脚本绕过 v3 约束。

### 13.2 并行运行

- v2/v3 使用不同 Compose project、网络、数据库 schema 和公开路径，避免状态串扰。
- 按 Agent 切换，不执行全量一次性迁移。
- 切流后至少观察错误率、首 token、检索空召回、citation 和用户反馈。
- 观察期内通过 Gateway 路由快速回退 v2；不要在故障中修改 v3 Revision 内容。

### 13.3 v3 版本回退

- 数据库迁移采用 expand/contract：先增加兼容字段和表，所有实例升级后再删除旧结构。
- Core 和 Runner 至少兼容当前及前一个 Runtime contract version。
- 应用回退前验证数据库 schema、Runtime digest 和 Bundle contract 是否仍兼容。
- 不可逆迁移必须有备份恢复演练和明确维护窗口。

## 15. 风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| Core 模块化单体成为较大故障域 | 多能力同时不可用 | 保持模块边界、超时/熔断、独立后台 Worker；数据库和 Runtime 不与 Core 同进程 |
| 内部无 Token 导致恶意容器可调用内部 API | 越权和数据泄露 | v3 只允许固定 Runtime；严格网络分区；只有 Runner 可创建容器；未来不可信场景改用 mTLS |
| Runner 持有 Docker 权限 | Runner 被攻破可能控制宿主机 | rootless Docker、无公开端口、最小 DB 权限、严格 allowlist、固定镜像和独立审计 |
| UI 全流程引入长任务和状态竞争 | 重复构建或状态错乱 | Job lease、幂等键、不可变 Revision、乐观锁和显式状态机 |
| 模块合并造成行为回归 | v2 功能或质量下降 | 先建契约测试和固定评测基线，再逐模块迁移 |
| v2 人工迁移耗时 | 发布延期 | 按 Agent 盘点和排序；模板化迁移清单；允许 v2/v3 有期限并行 |
| Artifact/Milvus/PostgreSQL 恢复点不一致 | Revision 无法运行 | 联合备份清单、恢复后完整性审计、缺失资源时禁止部署 |
| 通用 Runtime 无法表达部分旧 Agent | 个别业务无法迁移 | 明确列为 v3.0 非目标，保留 v2 或单独设计后续受控扩展机制 |
