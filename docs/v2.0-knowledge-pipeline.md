# 知识 Pipeline 与评测

阶段 4 的 Knowledge Worker 是本地、受控的写侧工具。`muye-data` 保持只读，只在
`ResourceSnapshotV1` 完整校验通过后加载已发布资源；它没有建库、写入、更新或删除 HTTP API。

`config/knowledge/<slug>.yaml` 仍是阶段 3 Generator 的逻辑输入。源文件构建配置必须放在独立的
`config/knowledge-sources/<slug>.yaml`，避免两种不同 schema 占用同一路径。

```yaml
schema_version: muye.ai/knowledge-source-config/v1
knowledge_id: kb.product_handbook
resource_id: kb.product_handbook
slug: product-handbook
display_name: 产品手册
sources:
  - path: product-handbook
    include: ["**/*.pdf", "**/*.docx", "**/*.md", "**/*.txt"]
parser_profile: docling-default-v1
embedding_alias: text-embedding-default
embedding_revision: r1
embedding_dimensions: 1024
connection: milvus_default
chunking:
  max_characters: 1200
  overlap_characters: 120
  min_characters: 80
keyword_analyzer: jieba
default_pipeline: hybrid
rerank_alias: text-rerank-default
rerank_required: false
evaluation_set_ref: knowledge-evaluations/product-handbook.yaml
max_source_files: 1000
max_total_source_bytes: 104857600
max_pdf_pages: 1000
max_docx_archive_entries: 10000
max_docx_uncompressed_bytes: 104857600
max_parsed_blocks: 100000
max_chunks: 10000
max_total_chunk_characters: 20000000
embedding_batch_size: 64
```

`sources.path` 和 `evaluation_set_ref` 都只能是相对路径。CLI 的 `--import-root` 是显式导入根；源文件、
中间目录和符号链接均会在规范化后检查，不能通过 `..`、绝对路径或 symlink 离开该根。配置不包含
Milvus 物理 Collection、URL 或凭据。

## 解析器

Markdown 和 TXT 使用确定性 UTF-8 段落解析。PDF/DOCX 的 `docling-default-v1` 使用关闭 OCR 的
Docling；安装解析 Worker 依赖：

```bash
.venv/bin/python -m pip install -r requirements-knowledge-docling.txt
```

扫描 PDF 未提取到文本时，默认返回 `OCR_REQUIRED`，不会把空文档发布。PDF 总会显式配置
`PdfPipelineOptions.do_ocr=false`；部署独立 OCR Worker capability 时安装
`requirements-knowledge-ocr.txt`，并在命令中显式使用 `--ocr-available`，此时固定使用 Paddle OCR，缺少
Paddle 依赖即失败，不回退至第三方默认 backend。任何乱码、空文本、控制字符、超出单文件/总字节、PDF 页数、
DOCX ZIP 条目/解压字节、blocks 或 chunks 预算的输入均会阻止整个版本发布。Embedding 按
`embedding_batch_size` 分批发送，在批次之间响应取消；单个请求最多 256 条和 100 万字符。

每份文档输出 `ParsedDocumentV1`，每个 block 和 chunk 都保存相对源路径、行/页/段落 locator、
原文件 checksum、block ID、content hash 和 citation ID。知识正文始终被视为不可信数据，不会作为
配置、Prompt、代码或 Milvus DSL 执行。

## 构建与确认

以下命令均通过根目录 wrapper 运行，实际凭据仅从环境注入：

```bash
./scripts/muye.sh knowledge propose-schema product-handbook --import-root /data/import
./scripts/muye.sh knowledge approve-proposal product-handbook --checksum <proposal-sha256> --approved-by <principal>
./scripts/muye.sh knowledge build product-handbook --import-root /data/import
```

Proposal checksum 变化后必须重新确认。构建时 Planner 从确认的 Proposal 确定性派生
`CollectionIndexPlanV1`：固定 `chunk_id` 主键、版本/文档/来源字段、`content` analyzer、Dense
`embedding`、BM25 Function 生成的 `sparse_embedding`、`FLAT + COSINE` 和
`SPARSE_INVERTED_INDEX + BM25` 索引。每个 KnowledgeVersion 使用新的不可变 Collection；同名既有
Collection 只做 schema 验证，Worker 不删除、truncate、upsert 或修改既有版本。

构建会写入以下受控 artifact：

- `config/generated/knowledge-proposals/<slug>/current.json`
- `config/approvals/schema/<slug>.json`
- `config/generated/knowledge-manifests/<slug>/<knowledge-version>.json`
- `config/generated/resource-snapshot.candidate.json`
- `config/generated/knowledge-jobs/` 与 `config/generated/knowledge-reports/`

最后两个 Job 目录是运行记录，不应手工修改；JSON 均采用原子 replace 写入。通过
`knowledge status <job-id>` 查看状态，`knowledge cancel <job-id>` 请求协作式取消。`knowledge retry` 会同步
执行新的 attempt，不会创建无执行者的 `QUEUED` 记录：重试 build 必须给出原导入根及可选 OCR/LLM/Milvus 参数，
重试 evaluate 只可给出候选 `--data-url`。重试会重新计算当前输入 checksum，任何 Proposal、Manifest 或
EvaluationSet 漂移都被拒绝。

## 评测与发布

评测集放在 `config/<evaluation_set_ref>`，使用 `EvaluationSetV1` 固定问题、相关 chunk、要求的 citation、
Recall@K、MRR 和 citation coverage 门槛。每个版本会评测 Dense、BM25、Hybrid RRF，以及配置了 rerank
时的 Hybrid + Rerank。所有必需 pipeline 都通过门禁才允许发布。

候选快照必须由隔离的 `muye-data` 实例加载，不能指向生产 active Snapshot。例如为该实例设置：

```bash
export MUYE_DATA_RESOURCE_SNAPSHOT_PATH=../config/generated/resource-snapshot.candidate.json
```

再运行：

```bash
./scripts/muye.sh knowledge evaluate product-handbook --data-url http://127.0.0.1:9840
```

评测前、评测后和发布锁内，Worker 都会通过 `GET /api/v1/snapshot-identity` 核对隔离实例加载的 Snapshot
revision/checksum、Resource revision/checksum、KnowledgeVersion 和 Collection Plan checksum；指向生产、旧 candidate
或评测期间替换 candidate 的实例均会失败。评测失败只写报告并保留 active Snapshot。成功时 Worker 原子替换
`config/generated/resource-snapshot.json`。生产 `muye-data` 设置同名环境变量指向 active 文件，并按
`MUYE_DATA_RESOURCE_SNAPSHOT_POLL_SECONDS` 轮询；候选 schema/checksum/connection/pipeline 任一无效时
重载会被拒绝，内存中的上一快照继续服务。候选首次引用配置中已声明但尚未使用的 connection 时，服务会 staging
构造并验证其只读 backend；失败时不会替换当前资源或 backend 表。
